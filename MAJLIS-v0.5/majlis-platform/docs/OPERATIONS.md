# Эксплуатация

## Локально

1. Docker должен быть запущен.
2. В PyCharm откройте `majlis-platform/main.py`, выберите интерпретатор с установленными requirements.lock и нажмите Run.
3. Дождитесь строки «Бот @majlis_test_bot запущен».
4. В Telegram отправьте новый `/start` и нажмите кнопку кабинета.

Если видите `no tunnel`, закройте окно Mini App, дождитесь восстановления в консоли, откройте актуальное меню бота или отправьте новый `/start`. Старое сообщение содержит старый URL. Launcher отслеживает новую регистрацию URL и проверяет публичный /health; после двух неудачных периодических проверок пересоздаёт туннель и обновляет меню. Если восстановление не удалось после трёх попыток, запуск завершается с понятной ошибкой.

localhost.run — временная среда тестирования. Домен может меняться и соединение может прерываться; это ограничение сервиса, описанное в [документации](https://localhost.run/docs/forever-free/). Бот не обеспечивает круглосуточную доступность при выключенном компьютере.

Для просмотра заказов не нужен доступ менеджера. В пустой рабочей базе отображается «Здесь появятся ваши заказы»; демонстрационные покупки автоматически не создаются.

## Сервер со своим доменом

Этот профиль подготовлен для развёртывания. Без реального сервера и домена его публичная доступность не проверяется.

В локальном `.env` сервера задайте BOT_TOKEN, разные пароли администратора, мигратора и приложения, HEALTH_TOKEN, MANAGER_IDS только для согласованного менеджера, APP_DOMAIN (hostname без https://). DNS домена должен указывать на сервер, порты 80/443 должны быть доступны. Не используйте пароль с двоеточием, @, слешем или пробелом без URL-кодирования DATABASE_URL; secrets.token_urlsafe подходит для приведённой схемы.

```sh
docker compose --env-file .env -f compose.server.yaml up -d --build
```

Compose сначала запускает БД, применяет миграции, затем API, bot, notify и Caddy. PostgreSQL не публикует порт на сервере; наружу открывается только HTTPS-прокси. API-контейнер работает без root, с read-only filesystem и no-new-privileges. Логи Uvicorn не содержат URL/initData. Caddy ограничивает размер body и завершает TLS. Не включайте логирование Telegram request URL: он содержит ключ.

Кнопки в сообщениях и меню настраиваются через Bot API. Кнопка запуска **в профиле** и Main Mini App требуют отдельной настройки в BotFather: `/mybots` → бот → Bot Settings → Configure Mini App → Enable Mini App, указать стабильный HTTPS-адрес. Эта настройка в BotFather не выполнена автоматически; ссылки `?startapp` до её включения не заявляются рабочими. [Источник Telegram](https://core.telegram.org/bots/webapps#launching-mini-apps)

Для обновлений сначала создайте backup, затем обновите исходники и снова выполните Compose build/up. Применённые SQL-миграции не редактируют: добавляют новый файл. Мигратор проверяет SHA-256 ранее применённых файлов и использует advisory lock.

Обновление значений POSTGRES_PASSWORD в `.env` не меняет пароль в уже созданной базе. Смена паролей требует отдельной согласованной процедуры; автоматическая ротация не выполняется.

## Резервные копии

```sh
python manage.py backup
python manage.py inspect-backup --file data/backups/ИМЯ.dump
```

Для server Compose добавьте `--server`. Копия создаётся pg_dump в формате custom, с правами файла 0600. Проверка inspect подтверждает лишь читаемость архива. Регулярное расписание, шифрование, перенос копии на другой носитель и оповещения в этой версии не настроены. Рекомендуемая операторская процедура: ежедневный backup и периодическая проверка восстановления в отдельной базе; сроки хранения согласовать с владельцем.

Восстанавливайте сначала в **новую отдельную базу**, например `majlis_restore_test`, через pg_restore `--no-owner --exit-on-error`. Не выполняйте `--clean` для рабочей базы без отдельного плана восстановления и подтверждения владельца. Docker `down` сохраняет volumes; `down -v` удаляет данные — не используйте его для обычной остановки.

## Проверки

`/health` подтверждает процесс и его instance_id; `/ready` требует секретный заголовок X-Health-Token и проверяет соединение с PostgreSQL и применённые миграции. Счётчики очереди доступны менеджеру. Внешний мониторинг, алерты, метрики, автоматическое расписание backup и нагрузочное тестирование пока не внедрены.

Тесты требуют отдельную базу с суффиксом `_test`, отдельные runtime/migration роли и одинаковую целевую БД в TEST_DATABASE_URL и TEST_MIGRATION_DATABASE_URL. Административная подготовка описана в TESTING.md. Они отказываются работать с именем без суффикса `_test` и очищают только тестовую базу.

```sh
python -m pip install -r requirements-dev.txt
python -m pytest -q tests
```

## Репетиция восстановления 0.5

```sh
python manage.py backup
python manage.py restore-test --file data/backups/ИМЯ.dump --target majlis_restore_unique_test
```

Команда создаёт только новую БД с суффиксом `_test`; существующую не перезаписывает. Нет `--clean`. После восстановления сравниваются 9 таблиц, хеши строк, структура ограничений, проверяются 12 фактических нарушений ограничений в rollback. Это малый интеграционный тест, не гарантия больших объёмов. Если источник меняется после dump, сравнение снимков может не совпасть: повторяйте на согласованном snapshot без конкурентной записи. Восстановление умышленно исключает владельцев/ACL; применяйте production-права отдельно.

`--container ИМЯ` позволяет использовать существующий локальный контейнер БД вместо Compose. Применяйте только собственные доверенные резервные копии: PostgreSQL dump может содержать исполняемые SQL-объекты. Тестовую БД после проверки не удаляет автоматика. Расписание, шифрование/вынос копий, retention и алерты требуют настройки инфраструктуры. Секрет HEALTH_TOKEN не публикуйте; он нужен только локальным healthcheck.

Public limiter действует на процесс и непосредственный IP соединения; за туннелем/NAT он может быть общим для нескольких пользователей. Значение PUBLIC_REQUESTS_PER_MINUTE подбирается измерениями. X-Forwarded-For игнорируется намеренно. Для нескольких реплик нужен общий edge limiter и нагрузочная приёмка.
