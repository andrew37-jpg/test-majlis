# Обновление существующей установки 0.4 → 0.5

Архив подготовлен отдельно. Рабочая база и исходники на Desktop не изменялись.

1. Не распаковывайте поверх `.env`/data/venv. Сохраните текущие исходники, конфигурацию и резервную копию; сначала проверьте restore в новой отдельной базе. Не запускайте двух polling-ботов с одним токеном.
2. Для изменения владельцев объектов существующей БД требуется административная операция: остановите старые API/бот/уведомления и получите разрешение владельца. Проверьте имена объектов и пароли локально. SQL `docker/upgrade-existing.sql` подготовлен для текущих имён `majlis`, `majlis_app`, `majlis_migrator`, но **не был выполнен на рабочей БД**. Роль migrator создаётся только если отсутствует; пароль существующей роли не меняется. Скрипт не использует REASSIGN OWNED и не изменяет другие БД.
3. Укажите отдельный `POSTGRES_MIGRATION_PASSWORD`, `MIGRATION_DATABASE_URL`, `HEALTH_TOKEN` в .env. DATABASE_URL остаётся runtime-ролью. Изменение строки .env не меняет существующие пароли PostgreSQL. Секреты не переносите в отчёты или чат.
4. Примените `python -m majlis.cli migrate`. 001 неизменна; 002 добавляет поля владельца/последовательности, сохраняя существующие строки. История переданных ранее заказов консервативно скрывается от покупателей, остаётся у менеджера. Проверьте политики и при необходимости отдельно разберите legacy-принадлежность с заказчиком, а не исправляйте её массово наугад.
5. Проверьте ограниченную runtime-роль: не владелец orders/schema, CREATE/ALTER/DROP/TRUNCATE, UPDATE/DELETE/SELECT audit и запись schema_migrations запрещены; обычные API-сценарии проходят. API и bot на сервере не получают MIGRATION_DATABASE_URL: он задан только сервису migrate.
6. Откройте папку новых исходников в PyCharm, выберите существующий интерпретатор с requirements.lock, проверьте рабочую директорию и Run main.py. Или выполните серверный Compose после проверки домена/среды. Это уже обновление рабочей среды, не автоматический шаг подготовки архива.
7. Telegram: открыть актуальное меню и новую кнопку кабинета; старые сообщения могут содержать прежний URL. Ручная приёмка: покупатель видит только свой заказ; передача очищает имя в форме, требует нового имени/подтверждения, сбрасывает платёжную ссылку; новый покупатель не получает прежнюю историю; старый — 404. Проверьте отправку согласованному тестовому получателю, не клиентам.

Rollback: сохраняйте копию схемы и данные до миграции. Новый код нельзя заменять старым в рабочей среде без проверки совместимости/прав; старая версия не знает поколений владельцев и может опять смешать историю. Восстановление поверх рабочей БД — отдельный согласованный аварийный план, не команда restore-test.
