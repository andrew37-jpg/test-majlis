# Обновление текущего нового проекта 0.5 → 0.6

Этот архив продолжает 0.5, не заменяет его другой архитектурой. Рабочая установка и её данные при подготовке пакета не менялись.

1. Сохраните прежние исходники, .env и резервную копию. Проверьте restore-test в новой базе. Не распаковывайте поверх локальных секретов и не запускайте второй polling с тем же токеном.
2. Если установка ещё 0.4, сначала выполните подготовку ролей/совместимости из UPGRADE-0.5.md. Архив 0.6 не делает административное обновление прав автоматически.
3. На согласованном окне остановите API/bot/notify и писателей интеграций. Используйте существующие секреты и отдельные runtime/migration роли. Runtime зависимости не изменены относительно 0.5; requirements.lock содержит хеши.
4. Из новой папки выполните `python -m majlis.cli migrate`. 001/002 идентичны 0.5; 003 добавляет kind и приватную mapping-таблицу, 004 классифицирует лишь подтверждённые аудитом прежние transfer-события. Мигратор проверяет контрольные суммы; не исправляйте ошибку checksum редактированием schema_migrations.
5. Обновите код целиком в пределах текущего проекта, включая web-модули. JSON события дополнены kind, прежние поля сохранены; старые status-события имеют default status. Публичные прежние endpoint сохранены. Новый /api/orders/commercial доступен менеджеру. Payment принимает пустой URL для удаления.
6. Запустите main.py в PyCharm с корректной рабочей директорией и .env. Дождитесь успешного публичного /health и настройки Telegram. Откройте свежее меню/отправьте новый /start: старый URL может быть недоступен. Перезагрузите Mini App, чтобы она получила новый JS.
7. Приёмка на согласованных тестовых аккаунтах: покупатель видит только своё; менеджер меняет сумму/товар и видит удаление старой ссылки; смена срока записывает историю, но не меняет дату checkpoint; копирование/удаление ссылки; передача не раскрывает прежнюю историю. Подтвердите реальную доставку уведомления только тестовому получателю.

Rollback: сохранённый snapshot и прежние исходники нужны до миграции. Не откатывайте вслепую: старый UI не различает новые типы истории и может показывать неверные даты checkpoint. Restore-test создаёт отдельную БД и не переносит production ACL; рабочее восстановление — отдельная согласованная процедура.

Подготовка старой БД заказчика отделена от обновления 0.5: LEGACY-MIGRATION.md. Реального источника нет; `apply-test` не предназначен для рабочей БД. Новые резервные копии сравнивают 10 таблиц и 15 нарушений ограничений.
