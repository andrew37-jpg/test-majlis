# Подготовка переноса, а не выполненная миграция старой базы

Старая схема/дамп/репозиторий заказчика не предоставлены. PostgreSQL текущего приложения — целевая схема НОВОГО бота. Базы прежних локальных тестов и резервные копии прототипа не считаются старой системой заказчика.

## Какие сведения нужны от старой системы

- Read-only экспорт/дамп и схема с версиями, кодировкой, часовым поясом, ограничениями и связями. Доступы/секреты передаются отдельно защищённо, не в JSON или чат.
- Стабильный ID заказа, номер заказа, клиент и подтверждённое соответствие клиента Telegram ID. Внутренний customer_id не равен Telegram ID по умолчанию.
- Товар/комплектация, сумма и её единица (рубли/копейки/иная валюта), партия/трек, ETA и значение «подтверждённая дата».
- Исходная дата создания заказа с часовым поясом, если она хранится; нельзя выводить её из даты импорта.
- Все фактические состояния/переходы, история с timestamp + timezone, владельцы в момент события, разделение внутренних/клиентских комментариев, отмены/возвраты.
- Платёжные сервисы, связи invoice/order/customer, срок действия и порядок отмены ссылок, реальные статусы оплат. Старые URL нельзя слепо выдавать новым клиентам.
- Объёмы, дубли/битые связи, сверочные суммы/количества, требования к архиву и основанию хранения.

## Нормализованный контракт целевого приложения

`docs/normalized-export.schema.json` — JSON Schema собственного ВХОДНОГО контракта, **не описание старой базы**. `examples/normalized-export.synthetic.json` — только вымышленные данные. После получения старой схемы нужен отдельный явный mapping/экспортёр; текущий код не пытается угадать её таблицы или поля.

`schema_version=1`, `source` — стабильное согласованное пространство источника. Каждая запись содержит source_order_id, order в целевых полях, явные currency=RUB и telegram_id_verified=true, согласованный status. Сумма — целые копейки, без автоматического угадывания/конвертации валют. Неизвестный status отклоняется: нужен утверждённый mapping, а не fuzzy-перевод.

source_created_at — исходная дата создания, если известна; явный timezone обязателен. Без неё dry-run выдаёт предупреждение, а created_at новой целевой записи означает время импорта, не предположительную старую дату. imported_at в mapping фиксирует сам перенос отдельно.

История требует явного timezone. Неизвестный владелец сохраняется как неизвестный, поколение 0 — доступ только менеджеру. Для показа покупателю необходимы owner_verified=true, его фактический owner_telegram_id и visible_to_customer=true; они должны совпадать с текущим подтверждённым покупателем. История не перепривязывается произвольно. Payment URL принимается только при явном подтверждении связи и разрешённом HTTPS-домене; лучше опустить неподтверждённые/истёкшие ссылки. Это не подтверждение оплаты у провайдера.

Пределы первого batch: 8 MiB, 1000 заказов, 500 событий на заказ. Нельзя молча обрезать большие истории: заранее разбить согласованно или расширить контракт с проверками. Файлы реального экспорта содержат персональные данные и не должны попадать в исходники/публичные отчёты.

## Dry-run и репетиция

Из папки приложения:

```sh
python -m majlis.legacy_import inspect --file examples/normalized-export.synthetic.json
python -m majlis.legacy_import inspect --file PRIVATE_EXPORT.json --check-target
python -m majlis.legacy_import rehearse --file PRIVATE_EXPORT.json
python -m majlis.legacy_import rehearse --file PRIVATE_EXPORT.json --apply-test
```

Первый inspect не читает настройки/БД и не пишет данные. Проверяет формат, дубли внутри файла, обязательные подтверждения. Платёжные ссылки без сверки allowlist не считаются готовыми. --check-target использует мигратор в READ ONLY для поиска конфликтов целевой схемы; прежде примените 001–004. Отчёт выводит только количества, номера строк и коды, не имена/ссылки/ID клиентов.

rehearse без --apply-test — dry-run по отдельной тестовой целевой базе. --apply-test допускается только в БД с суффиксом _test при двух ролях на одной базе. Даже функция записи проверяет current_database(). Рабочий import-командный режим намеренно не добавлен: данных и согласованной процедуры cutover пока нет.

Запись атомарна: при конфликте весь batch откатывается. Существующие заказы не перезаписываются. Пара source/source_order_id сохраняется в приватной legacy_imports; повтор идентичной записи пропускается, другая нагрузка под тем же ID блокируется. Одновременные batches одного источника сериализуются. Изменения менеджера после импорта не заменяются повтором старого экспорта. Уведомления не создаются: репетиция/массовый перенос не должен рассылать старые checkpoints клиентам.

## Реальный переход — ещё не выполнен

Сначала read-only исследование старого источника, mapping, репетиция на копии, сверка всех сущностей/сумм/истории/платежей/прав. Затем согласованный freeze/дельта, backup и restore, план отката, отдельное подтверждение рабочих операций, перенос и приёмка покупателем/менеджером. Идентичность source/order/customer следует подтвердить до запуска. Репетиция synthetic-файла не является переносом базы заказчика.
