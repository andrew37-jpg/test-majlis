# Кабинеты и назначенные права — 0.7

Авторизация остаётся Telegram initData с серверной HMAC-проверкой. Общий адрес UI открывает покупателя по умолчанию; рабочий адрес менеджера отделён. X-MAJLIS-Cabinet выбирает лишь контекст buyer/manager; сервер заново устанавливает доступ на каждом запросе. Покупатель не получает роль по заголовку.

Существующее правило сохранено: только явно перечисленные MANAGER_IDS имеют глобальный доступ. Это прежняя административная настройка, не автоматическое право любого менеджера. Текущий список пользователя не изменяется.

Для остальных менеджеров: manager_access.enabled разрешает кабинет, can_create отдельно разрешает создание. order_managers назначает конкретный заказ; can_edit=false означает только просмотр. Без назначения заказ отсутствует в списке/сводке/поиске/карточке/истории/очереди. Менеджер с can_create получает назначение только на созданный им заказ. В покупательском кабинете этот же человек видит лишь собственные покупки и свою историю текущего поколения, без действий менеджера.

Права нельзя назначить через Mini App, Bot API-команду или runtime SQL UPDATE. Не назначайте реальный ID по догадке. Для выдачи прав оператор с отдельной ролью мигратора должен подтвердить Telegram ID, заказ и объём доступа. Пример SQL параметризованного операторского действия (не запускается автоматически):

```sql
BEGIN;
-- :manager_id — предварительно проверенный Telegram ID существующего users.
INSERT INTO manager_access(telegram_id,can_create) VALUES (:manager_id,false)
ON CONFLICT(telegram_id) DO NOTHING;
INSERT INTO order_managers(order_id,manager_id,can_edit)
VALUES (:order_id,:manager_id,false)
ON CONFLICT(order_id,manager_id) DO UPDATE SET can_edit=excluded.can_edit;
COMMIT;
```

Отзыв: UPDATE manager_access SET enabled=false WHERE telegram_id=:manager_id. Расширение can_edit/can_create требует отдельного решения оператора. Общего переключателя в интерфейсе нет. Переход между отдельными страницами создаёт новый контекст без переноса списков/черновиков. При 403 данные активного кабинета убираются.

Блокирующая проверка назначения выполняется внутри транзакции действия через две миграторские функции с фиксированным SQL, квалифицированными именами таблиц, search_path=pg_catalog и отозванным PUBLIC EXECUTE. Runtime получает только EXECUTE, а не UPDATE таблиц прав. Это позволяет блокировать конкурентный отзыв права до завершения проверенного действия. Права заказов проверяются также при прямых запросах.

Граница: прикладной ACL проверяет API; это не PostgreSQL RLS для каждого Telegram-пользователя. Секрет runtime даёт самой службе доступ к заказам, поэтому он остаётся только на backend. Основание устройства SECURITY DEFINER: [PostgreSQL CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY).

## Уточнение: отдельная учётная запись менеджера

Общего переключателя ролей больше нет. Покупательский адрес `/` не показывает вход менеджера. Рабочий адрес `/manager/` открывает менеджерский контекст; без назначенного Telegram ID API вернёт 403. Ссылка сама по себе не даёт прав. Авторизация берёт ID из подписанных Telegram initData, а не из вручную введённого числа.

Менеджер использует собственный Telegram-аккаунт. Команда `/manager` проверяет отправителя и выдаёт рабочую ссылку только назначенному сотруднику. Команда не включена в общее меню. Если у человека есть оба назначения, его покупки остаются по `/`, рабочие данные — по `/manager/`; общедоступной кнопки выбора роли нет.

`manager_access.all_orders=true` явно назначает полный доступ к заказам. `can_read_inbox=true` отдельно разрешает все обращения клиентов. Даже прежние глобальные MANAGER_IDS не получают доступ ко всем сообщениям без этого флага. Назначение полного рабочего аккаунта требует конкретного подтверждённого ID и решения владельца; текущий ID покупателя не изменяется автоматически.

Лента активности показывает фактически записанные изменения доступных заказов. Обращения — тексты из Mini App и личного чата с этим ботом. Просмотры экранов, личные переписки вне бота, звонки и действия на неподключённом сайте не собираются. Вложения представлены типом и подписью, их файлы не скачиваются. Исходящие ответы менеджера и уведомления о новых обращениях пока не реализованы; реальных отправок клиентам для проверки не выполняют.

Пример согласованного полного назначения (оператор с миграторскими реквизитами; ID уже должен существовать в users):

```sql
INSERT INTO manager_access(telegram_id,enabled,can_create,all_orders,can_read_inbox)
VALUES (:verified_manager_id,true,true,true,true)
ON CONFLICT(telegram_id) DO UPDATE SET enabled=true,can_create=true,all_orders=true,can_read_inbox=true;
```

Это пример процедуры, не выполненное назначение пользователя. Учётные записи и пароли Telegram не запрашиваются; нужен только подтверждённый числовой ID.
